# 📊 좋은 코드, 나쁜 코드 6~8장 종합 비교 분석 리포트

**비교 대상**: `루덴스`, `모아`, `은오`, `현미밥` 크루 (사이클 2 코드 기준)

> 본 리포트는 모든 원칙에 대해 **"어떤 코드가 왜 좋은지(✅ Good)"** 와 **"어떤 코드가 왜 부족한지(❌ Bad)"** 를 실제 크루들의 코드를 통해 1:1로 비교 분석합니다.

---

## 🎯 6장: 방어적 프로그래밍과 오해 방지

### 1. 매직값(Magic Value) 반환 금지

> ❓ **왜 지켜야 할까요?** 데이터가 없을 때 `null`이나 `-1`을 반환하면 NPE나 논리 버그가 발생합니다. 명시적 예외나 `Optional`을 사용해야 합니다.

**✅ [Good] 모아, 현미밥, 은오의 코드 (Optional 활용)**

```java
// 데이터 부재 시 Optional.empty()를 반환하고, 서비스에서 예외를 던지도록 강제함
public Reservation getReservation(Long id) {
    return reservationDao.findById(id)
            .orElseThrow(() -> new ReservationNotFoundException("존재하지 않는 예약입니다."));
}
```

**❌ [Bad] 루덴스의 코드 (예외 유출 방치)**

```java
// ThemeDao.java
public Theme findById(Long id) {
    // Optional로 감싸지 않아 결과가 없으면 EmptyResultDataAccessException 발생 → 500 에러 유발
    return jdbcTemplate.queryForObject(sql, rowMapper, id);
}
```

---

### 2. 널 객체 패턴(Null Object Pattern)의 신중한 사용

> ❓ **왜 지켜야 할까요?** 다건 조회 시 `null`을 넘기면 호출자가 매번 `if (list != null)` 검사를 해야 합니다. 빈 컬렉션을 반환해야 합니다.

**✅ [Good] 루덴스, 모아, 현미밥의 코드 (빈 리스트 자동 반환)**

```java
public List<Reservation> findAll() {
    // Spring JDBC는 결과가 없으면 알아서 빈 리스트(Empty List)를 반환함
    return jdbcTemplate.query(sql, rowMapper);
}
```

**❌ [Bad] 은오의 코드 (Null 파라미터 분기 허용)**

```java
// 파라미터로 null을 허용해버리면, "전체 조회"와 "조건 조회"가 하나의 함수에 우겨넣어짐 (역할 혼용)
public List<ReservationTime> findAllReservationTime(LocalDate date, Long themeId) {
    if (date == null && themeId == null) {
        return jdbcTemplate.query("SELECT * FROM reservation_time", mapper);
    }
    // ...
}
```

---

### 3. 예상치 못한 부수 효과(Side Effect) 제거

> ❓ **왜 지켜야 할까요?** 내부에서 몰래 상태를 바꾸거나 무거운 의존성을 가지면 단위 테스트가 불가능해지고 버그 추적이 어렵습니다.

**✅ [Good] 루덴스의 코드 (시간 부수효과 외부화)**

```java
@Service
public class ThemeService {
    private final Clock clock; // 시간 의존성을 외부에서 주입받음

    public void doSomething() {
        LocalDate today = LocalDate.now(clock); // 테스트 시 시간을 마음대로 고정 가능!
    }
}
```

**❌ [Bad] 은오의 코드 (과도한 이중 방어 및 부수 효과)**

```java
// ReservationService.java
Long generatedId = reservationUpdatingDao.insert(reservationReq);
// 저장 직후 바로 다시 조회를 시도하고 중복 예외를 또 잡는 등 로직이 혼재됨
Reservation findReservation = reservationQueryingDao.findReservationById(generatedId)
        .orElseThrow(...);
```

### 4. 입력 매개변수 수정 금지

> ❓ **왜 지켜야 할까요?** 함수에 넘어온 객체를 몰래 수정하면, 원본 객체를 쓰던 외부 로직에 사이드 이펙트가 발생합니다.

**✅ [Good] 현미밥의 코드 (Copy-on-write 패턴)**

```java
// 원본(this)을 훼손하지 않고, 새로운 Builder 복사본을 만들어 반환
public Reservation reschedule(LocalDate date, ReservationTime time) {
    return Reservation.builder()
            .id(this.id).name(this.name).theme(this.theme)
            .date(date).time(time)
            .build();
}
```

**❌ [Bad] 은오의 코드 (불변성 의도 누락)**

```java
public class Reservation {
    private Long id; // final 키워드가 없어 언제든 Setter로 수정될 수 있는 가변 상태로 방치됨
}
```

---

### 5. 중요 입력은 필수 매개변수로 지정 (빠른 실패)

> ❓ **왜 지켜야 할까요?** 파라미터가 `null`일 때 무시하고 넘어가면(조용한 실패), 나중에 엉뚱한 곳에서 시스템이 터집니다.

**✅ [Good] 루덴스, 모아의 코드 (Fast Fail)**

```java
// 1. DTO 컴팩트 생성자에서의 빠른 실패 (루덴스)
public CreateReservationRequest {
    if (date == null) throw new InvalidInputException("날짜 필수");
}

// 2. 컨트롤러 선언적 방어 (모아)
public ReservationResponse create(@Valid @RequestBody ReservationRequest req) { ... }
```

**❌ [Bad] 현미밥의 코드 (도메인 검증 누락)**

```java
// ReservationTimeFactory에서 null 체크 없이 바로 생성하여 쓰레기 값이 들어갈 위험 존재
public static ReservationTime create(LocalTime startAt, LocalTime finishAt) {
    return new ReservationTime(null, startAt, finishAt);
}
```

---

### 6. 미래를 대비한 열거형(Enum) 처리

> ❓ **왜 지켜야 할까요?** 에러나 상태를 단순 문자열이나 개별 클래스로 흩뿌리면 코드 파편화가 발생합니다.

**✅ [Good] 현미밥의 코드 (중앙집중형 Enum)**

```java
public enum ErrorCode {
    PAST_RESERVATION(HttpStatus.BAD_REQUEST, "지난 예약 불가"),
    NOT_FOUND(HttpStatus.NOT_FOUND, "존재하지 않음");
    // HTTP 상태와 메시지를 완벽하게 캡슐화
}
```

**❌ [Bad] 루덴스, 모아, 은오 (Enum 부재)**

- 개별적인 커스텀 예외(`XxxNotFoundException`, `YyyConflictException`)를 무수히 많이 생성하여 패키지가 비대해집니다.

## 🎯 7장: 견고한 데이터와 논리 설계

### 1. 객체를 깊은 수준까지 불변(Immutable)으로 설계하라

> ❓ **왜 지켜야 할까요?** 도메인 객체를 API 응답(DTO)에 그대로 욱여넣으면, 도메인이 변할 때 API 스펙이 즉시 박살납니다(캡슐화 파괴).

**✅ [Good] 모아의 코드 (철저한 레이어 분리)**

```java
// Controller는 Service DTO(Result)만 받고, Service는 Domain을 다룸
ReservationResult saved = reservationService.create(request.toCommand());
return ReservationResponse.from(saved);
```

**❌ [Bad] 루덴스의 코드 (도메인 객체 직접 노출)**

```java
public record ReservationResponse(
        Long id,
        String name,
        LocalDate date,
        ReservationTime time // 도메인 객체가 API 응답에 그대로 노출됨!
) { ... }
```

---

### 2. 지나치게 일반적인 데이터 타입 지양하라

> ❓ **왜 지켜야 할까요?** 시간 데이터를 단순 문자열(`String`)로 뭉뚱그리면, 컴파일러가 타입 오류를 잡을 수 없습니다.

**✅ [Good] 모아, 은오의 코드 (타입 유지)**

```java
public record ReservationTimeResult(Long id, LocalTime startAt) { } // LocalTime 속성 유지
```

**❌ [Bad] 루덴스의 코드 (타입 정보 훼손)**

```java
public record ReservationTimeResponse(Long id, String startAt) {
    public static ReservationTimeResponse from(ReservationTime time) {
        // 시간 객체를 강제로 String으로 변환하여 시간 연산이나 검증이 불가능해짐
        return new ReservationTimeResponse(time.getId(), time.getStartAt().toString());
    }
}
```

---

### 3. 시간을 표현할 때 정수(Int/Long) 사용 금지

> ❓ **왜 지켜야 할까요?** 시간을 `Long`으로 다루면 시각인지 기간인지 모호해집니다.

**✅ [Good] 전원 공통 (Java Time API 완벽 적용)**

```java
// 타임스탬프 Long 대신 의미가 명확한 객체 지향적 시간 타입 사용
private final LocalDate date;
private final LocalTime startAt;
```

---

### 4. 파생 데이터의 중복 저장 금지

> ❓ **왜 지켜야 할까요?** 실시간으로 도출 가능한 데이터를 굳이 캐싱하면 원본과 데이터 불일치가 발생합니다.

**✅ [Good] 루덴스의 코드 (상수를 활용한 실시간 계산)**

```java
// DB 컬럼에 넣지 않고 비즈니스 상수를 두어 쿼리로 실시간 파생(도출)함
private static final int POPULAR_THEME_PERIOD_DAYS = 7;
```

---

### 5. 중복된 논리 구조 통합 (진실의 원천 단일화)

> ❓ **왜 지켜야 할까요?** 쿼리나 검증 로직이 여러 곳에 복붙되어 있으면 유지보수 시 버그가 터집니다.

**✅ [Good] 모아의 코드 (SQL 진실의 원천 단일화)**

```java
// 가장 긴 조인 쿼리를 상수로 빼서 findAll, findById 등 모든 메서드가 공유함
private static final String SELECT_BASE = "SELECT r.id, ... FROM reservation r INNER JOIN ...";
```

**❌ [Bad] 루덴스, 은오의 코드 (복붙으로 인한 쿼리 중복)**

```java
// findById() 안에도 10줄짜리 쿼리, findAll() 안에도 10줄짜리 동일한 쿼리가 하드코딩됨
String sql = "SELECT r.id, ... FROM reservation r INNER JOIN ... WHERE r.id = ?";
```

## 🎯 8장: 모듈화와 추상화

### 1. 의존성 주입(DI)과 인터페이스 활용

> ❓ **왜 지켜야 할까요?** 구체 클래스에 직접 의존하면 훗날 기술 스택(JDBC → JPA) 교체 시 서비스 코드까지 다 뜯어고쳐야 합니다.

**✅ [Good] 모아, 현미밥의 코드 (인터페이스 주입 - DIP 준수)**

```java
// 서비스는 '인터페이스'에만 의존함 (구현체가 JDBC인지 JPA인지 알 필요 없음)
public ReservationService(ReservationRepository reservationRepository) { ... }
```

**❌ [Bad] 루덴스, 은오의 코드 (구체 클래스 직접 의존)**

```java
// 서비스가 JDBC 전용 '구체 클래스'에 강하게 결합됨
public ReservationService(ReservationDao reservationDao) { ... }
```

---

### 2. 상속(Inheritance)보다는 구성(Composition) 활용

> ❓ **왜 지켜야 할까요?** 상속을 남발하면 캡슐화가 깨집니다. 부모 대신 멤버 변수로 위임해야 합니다.

**✅ [Good] 모아의 코드 (Composition의 정석)**

```java
// UserReservationService가 AdminReservationService를 상속받는 대신 '주입(위임)'받음
public UserReservationService(AdminReservationService adminReservationService) {
    this.adminReservationService = adminReservationService;
}
```

---

### 3. 기능의 집중(디미터의 법칙)과 데이터 캡슐화

> ❓ **왜 지켜야 할까요?** 체이닝(`.get().get()`)으로 남의 객체 속을 털어오면, 객체 구조 변경 시 코드가 다 깨집니다.

**✅ [Good] 현미밥의 코드 (풍부한 도메인 모델)**

```java
// 서비스가 데이터를 꺼내 계산하지 않고, 객체 스스로 판단하게 시킴 (Tell, Don't Ask)
if (reservation.isPast()) { ... }
```

**❌ [Bad] 루덴스의 코드 (디미터의 법칙 위반)**

```java
public static ReservationResponse from(Reservation reservation) {
    return new ReservationResponse(
            reservation.getId(),
            reservation.getUser().getName() // User 객체 내부까지 파고드는 2단계 체이닝! (캡슐화 파괴)
    );
}
```

### 4. 반환 타입과 예외를 통한 세부 구현 유출 방지

> ❓ **왜 지켜야 할까요?** DB 관련 예외(`SQLException`)가 서비스 밖으로 유출되면 웹 계층이 하위 DB 기술에 종속됩니다.

**✅ [Good] 은오의 코드 (예외 상태코드 매핑)**

```java
// 500 에러를 숨기고 커스텀 비즈니스 예외에 404를 매핑하여 세부 기술 유출을 막음
@ResponseStatus(HttpStatus.NOT_FOUND)
public class ReservationNotFoundException extends RuntimeException { ... }
```

**❌ [Bad] 루덴스의 코드 (인프라 예외 직접 유출)**

```java
// UserDao.findById()에서 터진 EmptyResultDataAccessException이 그대로 유출되어
// 컨트롤러까지 날아가고 결국 클라이언트에게 원인 모를 500 에러를 반환함
```
