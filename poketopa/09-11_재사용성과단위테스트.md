# 📊 좋은 코드, 나쁜 코드 9~11장 종합 비교 분석 리포트 (사이클 2 기준)

**비교 대상**: `루덴스`, `모아`, `은오`, `현미밥` 크루

> 본 리포트는 "왜 이 원칙을 지켜야 하는가(Why)?"에 대한 설명과 함께 각 크루의 실제 코드 사례를 Good/Bad 1:1 매칭으로 분석합니다.

---

## 🎯 9장: 코드를 재사용하고 일반화할 수 있도록 하라

### 1. 암묵적인 가정을 피하고, 필요하다면 강제하라 (Fast Fail)

> ❓ **왜 지켜야 할까요?** 데이터베이스가 항상 값을 반환할 것이라거나, 사용자가 `null`을 넘기지 않을 것이라는 암묵적 가정은 코드 재사용 시 치명적인 버그(NPE 등)를 유발합니다. 반드시 명시적으로 검증해야 합니다.

**✅ [Good] 모아, 은오, 현미밥의 코드 (가정 배제 및 명시적 방어)**

```java
// DB 조회 결과가 없을 수도 있다는 것을 가정하지 않고 Optional로 명시적으로 감쌈
public Optional<Reservation> findById(Long id) { ... }
```

**❌ [Bad] 루덴스, 현미밥의 코드 (암묵적 가정의 위험)**

```java
// 1. 루덴스의 암묵적 가정 (DB 조회): 무조건 1개의 결과가 있을 것이라고 가정함
// 만약 결과가 없으면 EmptyResultDataAccessException이 발생해 500 에러를 뿜음
public Theme findById(Long id) {
    return jdbcTemplate.queryForObject(sql, rowMapper, id);
}

// 2. 현미밥의 암묵적 가정 (도메인 생성): startAt과 finishAt이 null이 아닐 것이라 가정함
// 만약 누군가 실수로 null을 넣고 호출하면, 방어 로직이 없어 시스템 어딘가에서 NPE 폭탄이 터짐
public static ReservationTime create(LocalTime startAt, LocalTime finishAt) {
    return new ReservationTime(null, startAt, finishAt);
}
```

### 2. 전역 상태를 피하고 의존성 주입(DI)을 활용하라

> ❓ **왜 지켜야 할까요?** 정적(static) 변수 등 전역 상태를 남용하면, 프로그램 곳곳에서 상태를 공유하므로 다른 목적으로 재사용할 때 서로 간섭하여 악성 버그를 유발합니다.

**✅ [Good] 전원 공통 (DI 완벽 활용)**

```java
@Service
public class ReservationService {
    private final ReservationRepository reservationRepository; // 전역 상태 배제

    // Spring의 생성자 주입(DI)을 사용하여, 특정 코드가 동일한 상태(Bean)를 공유할지
    // 아니면 테스트 환경처럼 독립적인 상태(Mock)를 가질지 완벽하게 제어하고 있음!
    public ReservationService(ReservationRepository reservationRepository) {
        this.reservationRepository = reservationRepository;
    }
}
```

### 3. 낮은 층위의 코드에서 기본 반환값을 주지 말고 상위 계층에 위임하라

> ❓ **왜 지켜야 할까요?** 하위 계층(DAO)에서 에러를 터뜨리거나 임의의 기본값을 반환해버리면, 상위 계층(Service)이 해당 코드를 재사용하면서 상황에 맞게 기본값을 다르게 제공할(Fallback) 통제권을 빼앗깁니다.

**✅ [Good] 은오 크루의 코드 (하위 계층의 올바른 위임)**

```java
// DAO(낮은 층위)에서는 에러를 덮거나 던지지 않고 빈 껍데기(Optional.empty)만 넘겨,
// Service(높은 층위)가 orElseThrow()를 할지 기본값을 줄지 결정하게 통제권을 넘김
public Optional<Theme> findById(Long id) {
    try {
        Theme theme = jdbcTemplate.queryForObject(sql, param, themeRowMapper);
        return Optional.of(theme);
    } catch (EmptyResultDataAccessException ex) {
        return Optional.empty();
    }
}
```

### 4. 함수는 필요한 데이터만 매개변수로 받도록 최소화하라

> ❓ **왜 지켜야 할까요?** 함수가 몇 개의 정보만 필요한데도 특정 문맥의 거대한 객체(DTO)를 통째로 받으면, 다른 문맥에서 그 함수를 재사용할 때 불필요한 더미 값을 억지로 채운 DTO를 만들어야 하는 혼란이 생깁니다.

**✅ [Good] 모아, 현미밥 크루의 코드 (도메인 기반 추상화)**

```java
// DAO가 특정 Controller DTO에 종속되지 않고, 도메인 객체(Reservation)를 받음.
// 나중에 웹 API가 아닌 '사내 스케줄러 자동 예약 로직'에서 DAO를 재사용할 때도 제약이 없음!
public Reservation save(Reservation reservation) { ... }
```

**❌ [Bad] 루덴스, 은오 크루의 코드 (Controller DTO에 강한 결합)**

```java
// DAO의 save 함수가 웹 계층의 전용 객체인 CreateReservationRequest DTO를 통째로 받음.
// 억지로 가짜(Dummy) CreateReservationRequest를 만들어야 하는 등 재사용성이 극도로 떨어짐.
public Long save(CreateReservationRequest request) { ... }
```

## 🎯 10장: 단위 테스트의 원칙

### 1. 훼손의 정확한 감지와 잘 설명되는 실패 (명확한 테스트 작성)

> ❓ **왜 지켜야 할까요?** 테스트가 실패했을 때 원인을 한눈에 파악할 수 없으면, 디버깅에 엄청난 시간이 낭비됩니다. 서술적인 이름이 필수적입니다.

**✅ [Good] 현미밥 크루의 코드 (명확한 DisplayName)**

```java
// 누구나 실패 원인을 즉시 파악할 수 있는 훌륭한 네이밍
@DisplayName("이미 지난 예약은 수정할 수 없다")
@Test
void updatePastReservation() { ... }
```

**❌ [Bad] 루덴스 크루의 코드 (@DisplayName 부재)**

```java
// @DisplayName이 없어 콘솔에서 수십 개의 테스트가 실패했을 때
// 어떤 비즈니스 요구사항이 깨졌는지 직관적으로 파악하기 다소 어려움
@Test
void findById() { ... }
```

---

### 2. 퍼블릭 API에 집중하되 부수 효과는 무시하지 말라

> ❓ **왜 지켜야 할까요?** 내부 프라이빗 변수나 로직을 검증하면 리팩토링 시마다 테스트가 깨집니다. 반면, DB 상태 변화 같은 중요한 부수 효과(Side Effect)를 무시하면 치명적인 버그를 놓칩니다.

**✅ [Good] 루덴스, 현미밥, 은오 크루의 코드 (최종 상태 검증)**

```java
// 내부적으로 어떤 메서드가 불렸는지 깐깐하게 묻지 않고,
// API 호출 후 DB에서 다시 조회했을 때 상태가 '최종적으로 어떻게 변했는가(부수 효과)'만 명확히 검증함
reservationService.deleteReservation(11L);
assertThat(reservationTimeService.getAvailableTimes(...)).hasSize(2);
```

---

### 3. 테스트 더블: 목(Mock)과 스텁(Stub)보다는 페이크(Fake)를 지향하라

> ❓ **왜 지켜야 할까요?** Mockito의 `@Mock`과 `verify`는 코드는 정상이지만 리팩토링으로 내부 메서드 구조만 바뀌어도 테스트가 깨지는 **플래키(Flakey) 테스트**를 양산합니다.

**✅ [Good] 현미밥, 은오, 루덴스 크루의 코드 (세부 구현과 독립적인 고전주의 테스트)**

```java
// Mockito를 거의 배제하고 @SpringBootTest 등을 통해 실제/H2 객체를 사용함으로써,
// '특정 메서드 호출 횟수'가 아닌 '진짜 도메인 동작'을 테스트함.
// 로직을 대대적으로 리팩토링해도 '기능'만 똑같이 동작하면 테스트가 든든하게 버텨줌!
```

**❌ [Bad] 모아 크루의 코드 (과도한 Mockito 사용으로 인한 결합도 증가)**

```java
// Service를 테스트하면서 Mock Repository의 특정 메서드가 1번 호출되었는지를 깐깐하게 검증함.
// 만약 existsByDate() 대신 findAll().stream()으로 성능 리팩토링을 진행하면,
// 비즈니스 로직이 정상이더라도 이 테스트는 무조건 실패함(거짓 양성).
verify(reservationRepository, times(1)).existsByDateAndTimeIdAndThemeId(...);
```

## 🎯 11장: 단위 테스트의 실제

### 1. 기능(함수명)이 아닌 동작을 테스트하라

> ❓ **왜 지켜야 할까요?** 해피 경로(성공 케이스)만 뭉뚱그려 테스트하면, 예외가 발생해야 할 상황(과거 날짜 예약 등)에서 시스템이 뚫려버립니다.

**✅ [Good] 현미밥 크루의 코드 (예외 동작의 꼼꼼한 분리 테스트)**

```java
// 단순히 create() 함수 하나만 테스트하는 것이 아니라,
// "이름이 null일 때", "과거 날짜일 때" 등 발생할 수 있는 모든 엣지 케이스(동작)를 별도로 검증함
@DisplayName("이름이 null이면 예외 발생")
@Test
void nameNull() {
    assertThatThrownBy(() -> factory.create(null, ...));
}
```

---

### 2. 공유 설정을 적절하게 사용하되, 가변 상태 공유를 피하라

> ❓ **왜 지켜야 할까요?** 한 테스트가 DB에 데이터를 넣고 지우지 않으면, 다음 테스트가 그 잔여 데이터 때문에 실패하게 됩니다. 테스트 간 독립성이 박살납니다.

**✅ [Good] 루덴스 크루의 코드 (매 테스트마다 DB 상태 초기화)**

```java
// 각 테스트 메서드마다 @Sql을 선언하여 가변 상태(DB)를 매번 초기화/세팅함으로써,
// 테스트 실행 순서에 상관없이 100% 독립적인 테스트 환경을 완벽하게 보장함
@Sql("classpath:data.sql")
@Test
void createTheme() { ... }
```

---

### 3. 적절한 어서션 확인자(Assertion Matcher)를 사용하라

> ❓ **왜 지켜야 할까요?** 단순히 `isTrue()`나 `isEqualTo(true)`로 검증하면 테스트 실패 시 "expected: true but was: false"라는 무의미한 에러가 뜹니다. 원인을 알 수 없습니다.

**✅ [Good] 현미밥 크루의 코드 (구체적인 AssertJ 체이닝 및 확인자)**

```java
// 단순히 에러가 났는지만 보지 않고, 커스텀 예외의 ErrorCode가 정확히 일치하는지까지 검증!
// 실패 시 "THEME_NOT_FOUND를 기대했는데 다른 에러다"라고 명확히 알려주어 디버깅 1초 컷 가능
assertThatThrownBy(() -> themeService.getById(999L))
        .satisfies(e -> assertThat(((BusinessException) e).getErrorCode())
                .isEqualTo(ErrorCode.THEME_NOT_FOUND));

// 리스트 크기 검증 시 isEqualTo(3) 대신 컬렉션 전용 확인자인 hasSize(3) 사용
assertThat(result).hasSize(3);
```

**❌ [Bad] (일반적인 안 좋은 예시)**

```java
// 만약 이렇게 짰다면, 실패 시 뭐가 문제인지 로그만 보고는 절대 알 수 없음
assertThat(result.size() == 3).isTrue();
```
