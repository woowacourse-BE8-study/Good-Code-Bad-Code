### 📋 핵심 개선 과제 (High Priority) 상세 분석

책에서 강조하는 **"신속하고 요란하게 실패하라(Fail Fast & Loudly)"**, **"오류를 숨기지 마라"**, **"명시적으로 오류를 전달하라"**는 원칙을 바탕으로 루덴스 코드의 핵심 문제점 4가지를 도출하고 개선 방향을 정리했습니다.

#### #1. `deleteReservation` — 존재 확인 없이 삭제 시도

**❌ 무엇이 문제인가? (루덴스 코드)**

`service/ReservationService.java`

```java
public void deleteReservation(Long id) {
    reservationDao.deleteById(id); // ← 존재 여부 확인 없음
}
```

`repository/ReservationDao.java`

```java
public void deleteById(Long id) {
    String sql = "DELETE FROM reservation WHERE id = ?";
    jdbcTemplate.update(sql, id); // ← 없는 id여도 그냥 실행, 0 rows affected
}
```

`jdbcTemplate.update()`는 삭제 대상 ID가 없어도 예외를 발생시키지 않고 `0`을 반환하며 조용히 종료됩니다. 이로 인해 Controller는 **`204 No Content`**를 응답하고, 클라이언트는 삭제가 성공했다고 착각하게 됩니다.

이는 책에서 경고하는 **"기본값 반환으로 오류를 숨기는 패턴"**의 전형입니다. 존재하지 않는 리소스 삭제 시도는 명백한 오류 상황임에도 이를 묵살하고 있습니다.

**✅ 어떻게 개선해야 하는가? (모아의 방식 적용)**

`service/ReservationService.java` (개선 방향)

```java
public void deleteReservation(Long id) {
    // 1. 존재 여부를 가장 먼저 확인 (Fail Fast)
    if (!reservationDao.existsById(id)) {
        throw new ReservationNotFoundException("존재하지 않는 예약입니다: id=" + id);
    }
    // 2. 확인 후 삭제 (정상 경로)
    reservationDao.deleteById(id);
}
```

**해결책**: `ReservationDao`에 `existsById()` 메서드를 추가하고, 삭제 전 반드시 리소스 존재 여부를 확인(**Fail Fast**)하여, 없을 경우 즉시 명확한 예외(**Fail Loudly**)를 던져야 합니다.

#### #2. `deleteTheme` — 참조 중인 예약 확인 누락 (FK 무결성)

**❌ 무엇이 문제인가? (루덴스 코드)**

`service/ThemeService.java`

```java
public void deleteTheme(Long id) {
    themeDao.deleteById(id); // ← 참조 중인 예약이 있는지 확인 안 함
}
```

테마(`Theme`)는 여러 예약(`Reservation`)에서 외래 키(FK)로 참조될 수 있습니다. 예약이 존재하는 테마를 삭제하려고 하면 DB 단에서 참조 무결성(FK) 제약 조건 위반으로 예외(`DataIntegrityViolationException`)가 발생합니다.

하지만 루덴스는 서비스 계층에서 이를 미리 확인하지 않고 DB에 삭제를 시도합니다. 발생한 DB 예외는 `GlobalExceptionHandler`에서 처리되지 않아 클라이언트에게 **`500 Internal Server Error`**로 반환됩니다.

클라이언트 입장에서는 "이 테마에 예약이 있어서 삭제 불가(409 Conflict)"라는 명확한 이유 대신, 서버가 고장 난 것으로 오해하게 됩니다.

**✅ 어떻게 개선해야 하는가? (모아의 방식 적용)**

`service/ThemeService.java` (개선 방향)

```java
public void deleteTheme(Long id) {
    if (!themeDao.existsById(id)) {
        throw new ThemeNotFoundException("존재하지 않는 테마입니다: id=" + id);
    }
    // 추가: 참조 중인 예약이 있는지 확인 (Fail Fast)
    if (reservationDao.existsByThemeId(id)) {
        throw new ThemeInUseException("예약이 존재하는 테마는 삭제할 수 없습니다: id=" + id);
    }
    themeDao.deleteById(id);
}
```

**해결책**: `ReservationDao`에 `existsByThemeId()` 메서드를 추가하여 삭제 전 참조 여부를 먼저 검증해야 합니다. DB 예외에 의존하지 않고 서비스 계층에서 **복구 가능한 오류를 명시적으로 전달**해야 합니다.

#### #3. `deleteReservationTime` — 사용 중인 시간 삭제 가능

**❌ 무엇이 문제인가? (루덴스 코드)**

`service/ReservationTimeService.java`

```java
public void deleteReservationTime(Long id) {
    reservationTimeDao.deleteById(id); // ← #2와 동일한 문제 (존재 및 참조 여부 미확인)
}
```

`#2`의 테마 삭제 문제와 완벽히 동일한 구조적 결함입니다. 예약 시간(`ReservationTime`) 역시 예약 엔티티에 의해 참조됩니다. 참조 중인 예약 시간을 삭제하면 DB 에러가 발생하고 **`500 Internal Server Error`**가 반환됩니다.

나아가 `ReservationTimeDao`에는 `existsById` 검증도 없어, 없는 ID 삭제 시 조용히 성공(204 응답)하는 `#1`의 문제도 동시에 갖고 있습니다.

**✅ 어떻게 개선해야 하는가? (모아의 방식 적용)**

`service/ReservationTimeService.java` (개선 방향)

```java
public void deleteReservationTime(Long id) {
    if (!reservationTimeDao.existsById(id)) {
        throw new ReservationTimeNotFoundException("존재하지 않는 예약 시간입니다: id=" + id);
    }
    // 추가: 예약 테이블 참조 확인
    if (reservationDao.existsByTimeId(id)) {
        throw new ReservationTimeInUseException("예약이 존재하는 시간은 삭제할 수 없습니다: id=" + id);
    }
    reservationTimeDao.deleteById(id);
}
```

**해결책**: `#1`, `#2`와 마찬가지로 `existsById`와 `existsByTimeId` 검증을 선행해야 합니다. 이를 위해 `ReservationTimeService`에 `ReservationDao` 의존성을 주입해야 합니다.

#### #4. `findById` — 없는 ID 조회 시 500 에러 반환

**❌ 무엇이 문제인가? (루덴스 DAO 전체)**

`repository/ReservationDao.java` 외 3개 DAO 동일

```java
public Reservation findById(Long id) {
    String sql = "SELECT ... WHERE id = ?";
    return jdbcTemplate.queryForObject(sql, rowMapper, id);
}
```

책은 **"Optional 같은 명시적 반환 타입을 활용해 값이 없을 수 있다는 사실을 메서드 시그니처 자체에 표현하라"**고 권장합니다.

루덴스의 `findById`는 무조건 객체를 반환하는 것처럼 선언되어 있지만, 실제 데이터가 없으면 `queryForObject` 메서드가 `EmptyResultDataAccessException`(런타임 예외)을 던집니다.

루덴스의 `GlobalExceptionHandler`는 이 예외를 처리하지 않기 때문에, 클라이언트는 `404 Not Found` 대신 **`500 Internal Server Error`**를 받게 됩니다. 오류를 숨기는 것을 넘어 더 나쁜 서버 오류로 둔갑시키는 결과입니다.

**✅ 어떻게 개선해야 하는가? (모아의 방식 적용)**

`repository/ReservationDao.java` (개선 방향)

```java
// 1. 반환 타입을 Optional로 변경하여 '값이 없을 수 있음'을 명시
public Optional<Reservation> findById(Long id) {
    String sql = "SELECT ... WHERE id = ?";
    // queryForObject 대신 query와 findFirst 활용
    List<Reservation> result = jdbcTemplate.query(sql, rowMapper, id);
    return result.stream().findFirst();
}
```

`service/ReservationService.java` (개선 방향)

```java
public Reservation getReservation(Long id) {
    // 2. 호출부에서 빈 케이스를 강제로 처리하도록 유도 (orElseThrow)
    return reservationDao.findById(id)
            .orElseThrow(() -> new ReservationNotFoundException("존재하지 않는 예약입니다: id=" + id));
}
```

**해결책**: DAO의 `findById` 반환 타입을 `Optional<T>`로 변경하여 "조회 결과가 없을 수 있음"을 계약(Contract)으로 명시합니다. 내부 구현은 예외를 던지는 `queryForObject` 대신 `query(...).stream().findFirst()`를 사용하고, 서비스(호출자)에서 `orElseThrow`로 명확한 도메인 예외를 던지도록 수정합니다.

### 💡 결론 및 핵심 교훈

루덴스 코드의 핵심 문제는 **DAO 계층이 작업의 '실패 가능성'을 타입과 메서드 시그니처로 표현하지 않았다**는 점에 있습니다. 모아의 코드는 `Optional`, `existsById`, `existsByXxx`와 같은 명시적인 수단을 통해 이 문제를 해결하고 있습니다.

루덴스에서 모아의 방향으로 나아가기 위한 3대 핵심 패턴은 다음과 같습니다.

1. **`findById`는 `Optional<T>`를 반환하라**: "값이 없을 수 있다"는 사실을 타입 시스템으로 명시.
2. **삭제(`delete`) 전 `existsById`로 선행 검증하라**: 오류를 숨기거나 DB 예외에 의존하지 않고, 발생 지점에서 즉시 포착(Fail Fast).
3. **범용 예외 대신 도메인 예외를 사용하라**: `IllegalStateException` 대신 `ReservationNotFoundException` 등을 사용하여 오류의 성격을 명확히 전달하고 HTTP 상태코드와 올바르게 매핑.

#### #1. 매직값(Magic Number) 제거: 설명되지 않은 값

**❌ 무엇이 문제인가? (모아 코드)**

`repository/JdbcThemeRepository.java` (모아)

```java
public List<PopularTheme> findPopular() {
    String sql = """
            SELECT t.id, t.name, t.description, t.thumbnail_url, COUNT(r.id) AS reservation_count
            FROM theme t
            INNER JOIN reservation r ON t.id = r.theme_id
            WHERE r.date >= DATEADD('DAY', -7, CURRENT_DATE) -- 🚨 Magic Number
              AND r.date <  CURRENT_DATE
            ...
            LIMIT 10 -- 🚨 Magic Number
            """;
    return jdbcTemplate.query(sql, POPULAR_ROW_MAPPER);
}
```

책은 **"계산식에 하드코딩된 숫자나 문자열은 다른 개발자가 의미를 알 수 없어 버그를 유발한다"**고 경고합니다. 모아의 쿼리에는 `-7`과 `10`이라는 숫자가 숨어 있습니다. 기획이 변경되어 "최근 14일, 5개"로 바뀌면 개발자는 SQL 내부를 파헤쳐야 하며, 해당 숫자가 무엇을 의미하는지 한눈에 파악하기 어렵습니다.

**✅ 어떻게 개선해야 하는가? (루덴스의 방식 적용)**

`service/ThemeService.java` (루덴스)

```java
// 💡 상수로 의미 부여 완벽
private static final int POPULAR_THEME_PERIOD_DAYS = 7;
private static final int POPULAR_THEME_END_OFFSET_DAYS = 1;
private static final int MAX_POPULAR_THEMES_LIMIT = 10;

public List<PopularThemeResponse> getPopularThemes(Integer limit) {
    limit = Math.clamp(limit, MIN_POPULAR_THEMES_LIMIT, MAX_POPULAR_THEMES_LIMIT);
    LocalDate to = today.minusDays(POPULAR_THEME_END_OFFSET_DAYS);
    LocalDate from = today.minusDays(POPULAR_THEME_PERIOD_DAYS);
    return themeDao.findPopularThemes(from, to, limit); // 변수로 전달
}
```

**루덴스의 훌륭한 점**: 기획 요구사항인 7일, 10개를 `POPULAR_THEME_PERIOD_DAYS` 등의 명시적 상수로 추출했습니다. 모아도 SQL 하드코딩을 제거하고, 루덴스처럼 서비스 계층에서 상수를 정의해 DAO에 파라미터로 넘겨주는 방식으로 개선해야 합니다.

#### #2. 거대한 함수 분리 (Extract Method) 및 조기 반환

**💡 무엇이 잘 되었는가? (모아 & 루덴스 공통)**

이 부분에서는 두 코드 모두 책의 원칙을 훌륭하게 따르고 있습니다.

`domain/Reservation.java` (모아)

```java
public Reservation(Long id, String name, LocalDate date, ReservationTime time, Theme theme) {
    validate(name, date, time, theme); // 1. 큰 흐름은 하나로
    ...
}

private static void validate(...) {
    validateName(name); // 2. 세부 책임별로 작게 분리
    validateDate(date);
    ...
}

private static void validateName(String name) {
    if (name == null || name.isBlank()) { // 3. 조기 반환 (Early Return)
        throw new IllegalArgumentException("예약자 이름은 비어 있을 수 없습니다.");
    }
}
```

**원칙 적용 우수 사례**: 중첩된 `if` 문을 사용하는 대신 **조기 반환(Early Return)**으로 조건을 평탄화했고, 생성자가 비대해지는 것을 막기 위해 `validateName` 등 기능 단위로 **작은 함수로 분리(Extract Method)**하여 추상화 계층을 나누었습니다. 루덴스 역시 `ReservationService`에서 중복 검증 로직을 `checkDuplicateReservation`으로 분리하여 좋은 가독성을 확보했습니다.

#### #3. 서술적인 네이밍 (이름으로 설명하기)

**❌ 무엇이 문제인가? (루덴스 코드)**

`exception/GlobalExceptionHandler.java` (루덴스)

```java
@ExceptionHandler(IllegalStateException.class)
```

`service/exception/` (모아)

```java
public class ReservationTimeInUseException extends RuntimeException { ... }
public class ThemeNotFoundException extends RuntimeException { ... }
```

책은 **"이름만으로 코드의 의도를 파악할 수 있도록 만들어야 한다"**고 강조합니다.

반면 모아는 `ThemeNotFoundException`, `ReservationTimeInUseException` 등 에러 클래스의 이름 자체가 **스스로 설명**을 담고 있습니다.

**✅ 어떻게 개선해야 하는가?**

루덴스도 모아의 예외 클래스 네이밍 전략을 도입하여, 발생 가능한 비즈니스 예외 상황들을 서술적인 이름을 가진 커스텀 예외 클래스로 분리해야 합니다.

#### #4. 자바 스트림과 람다의 올바른 사용

**❌ 무엇이 문제인가? (루덴스 코드)**

`service/ThemeService.java` (루덴스)

```java
public List<ThemeReservationTimeResponse> getThemeTimes(Long themeId, LocalDate date) {
    List<Long> reservedTimeIds = reservationDao.findTimeIdsByThemeIdAndDate(themeId, date);
    List<ReservationTime> reservationTimes = reservationTimeDao.findAll();

    return reservationTimes.stream()
            .map(time -> new ThemeReservationTimeResponse(
                    time.getId(),
                    time.getStartAt().toString(),
                    reservedTimeIds.contains(time.getId()) // 🚨 List 탐색 (O(N))
            ))
            .toList();
}
```

책에서는 **"작업에 적합한 도구를 선택하라"**고 조언합니다.

루덴스의 스트림 람다는 간결해 보이지만, 자료구조 선택의 아쉬움이 숨어있습니다. `reservedTimeIds`는 `List`이므로 `contains()` 메서드는 O(N)의 시간 복잡도를 가집니다. 이를 `map` 안에서 반복 호출하면 전체 시간 복잡도가 `O(N^2)`이 됩니다. (현재는 데이터가 적어 문제가 안 되지만, 좋은 패턴은 아닙니다.)

**✅ 어떻게 개선해야 하는가?**

```java
// 1. 작업에 적합한 도구 선택: List 대신 Set을 사용하여 contains() 성능을 O(1)로 개선
Set<Long> reservedTimeIds = new HashSet<>(reservationDao.findTimeIdsByThemeIdAndDate(themeId, date));

return reservationTimes.stream()
        .map(time -> new ThemeReservationTimeResponse(
                time.getId(),
                time.getStartAt().toString(),
                reservedTimeIds.contains(time.getId()) // 2. 이제 O(1)로 매우 빠름
        ))
        .toList();
```

또한, 객체를 생성하는 내부 로직이 3~4줄 이상 길어지거나 복잡해진다면, `private ThemeReservationTimeResponse toResponse(...)` 와 같은 **명명 함수로 추출**하여 스트림을 더 읽기 쉽게 유지할 수 있습니다.

### 💡 결론 및 핵심 교훈

5장 원칙을 적용해본 결과 두 코드베이스 모두 서로 배울 점이 명확히 드러났습니다.

1. **상수 추출 (루덴스 Win)**: 하드코딩된 숫자(Magic Number)는 코드의 독입니다. 루덴스처럼 기획 정책에 해당하는 숫자들은 반드시 상수로 추출해야 합니다.
2. **함수 분리와 조기 반환 (공통 우수)**: 중첩된 `if`문을 `Early Return`으로 해결하고, 하나의 거대한 함수를 `Extract Method`로 쪼개는 것은 클린 코드의 기본입니다.
3. **네이밍 (모아 Win)**: 범용 클래스를 오용하기보다, 해당 비즈니스를 정확히 설명하는 구체적이고 서술적인 이름(Custom Exception)을 사용해야 가독성이 극대화됩니다.
4. **람다와 성능의 조화**: 람다 내부 코드는 최대한 직관적이어야 하며, 람다 내부에서 반복되는 연산은 적절한 자료구조(`HashSet` 등)를 통해 비효율성을 제거해야 합니다.
