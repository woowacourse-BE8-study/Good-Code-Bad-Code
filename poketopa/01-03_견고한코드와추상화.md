# 좋은 코드, 나쁜 코드 1~3장 정리

## 1. 코드는 '친절한 가이드라인'이 아니라 '견고한 울타리'여야 한다

객체의 불변성을 보장하고, 잘못된 사용을 컴파일 단계에서 차단해야 한다.

### Entity: 외부에서 변경 불가능하도록 설계

```java
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED) // 기본 생성자 호출 자체가 불가능
@AllArgsConstructor
@Builder
public class ReservationTime {
    private Long id;
    private LocalTime startAt;
}
```

### DTO: `record`로 불변성 보장

```java
public record ReservationRequestDto(
        String name,
        @JsonFormat(pattern = "yyyy-MM-dd")
        LocalDate date,
        Long timeId
) {
    // record는 모든 필드가 private final, setter 없음 → 수정 자체가 불가능
}
```

## 2. 단일 계층 추상화

> 하나의 메서드 안에서 고수준 로직과 저수준 세부사항이 섞이면 안 된다.

### 좋은 예: 일관된 추상화 레벨

```java
public class ReservationService {

    private final ReservationDao reservationDao;
    private final ReservationTimeDao reservationTimeDao;

    public ReservationResponseDto create(ReservationRequestDto requestDto) {
        ReservationTime time = reservationTimeDao.findById(requestDto.timeId());
        Reservation saved = reservationDao.save(requestDto.toEntity(time));
        return ReservationResponseDto.from(saved);
    }
    // 시간 조회 → 예약 저장 → 응답 변환 / 일관된 depth
}
```

### 나쁜 예: 여러 추상화 레벨이 섞임

```java
// 레벨 1: 무엇을 (비즈니스 의도)
// 레벨 2: SQL 문자열
// 레벨 3: JDBC 접근
public Reservation save(Reservation reservation) {
    String sql = "INSERT INTO reservation (name, date, time_id) VALUES (?, ?, ?)";
    KeyHolder keyHolder = new GeneratedKeyHolder();              // 레벨 2

    jdbcTemplate.update(connection -> {                          // 레벨 3
        PreparedStatement ps = connection.prepareStatement(sql, new String[]{"id"});
        ps.setString(1, reservation.getName());
        ps.setDate(2, Date.valueOf(reservation.getDate()));
        ps.setLong(3, reservation.getTime().getId());
        return ps;
    }, keyHolder);

    Long generatedId = keyHolder.getKey().longValue();
    reservation.assignId(generatedId);
    return reservation;                                          // 레벨 1
}
```

### 개선: 레벨에 따라 분리

```java
public Reservation save(Reservation reservation) {
    // 레벨 1 메서드
    Long generatedId = executeInsert(reservation);
    reservation.assignId(generatedId);
    return reservation;
}

private Long executeInsert(Reservation reservation) {
    // 레벨 2~3 메서드
    String sql = "INSERT INTO reservation (name, date, time_id) VALUES (?, ?, ?)";
    KeyHolder keyHolder = new GeneratedKeyHolder();
    jdbcTemplate.update(connection -> {
        PreparedStatement ps = connection.prepareStatement(sql, new String[]{"id"});
        ps.setString(1, reservation.getName());
        ps.setDate(2, Date.valueOf(reservation.getDate()));
        ps.setLong(3, reservation.getTime().getId());
        return ps;
    }, keyHolder);
    return keyHolder.getKey().longValue();
}
```

## 3. 추상화 누수 방지

> **추상화 누수(Leaky Abstraction)**: 숨겨야 할 내부 사정이 밖으로 새어나와 사용자가 그걸 알아야만 하는 상황.

내부 구현 세부사항이 경계 바깥으로 새어나오면 안 된다.

### 나쁜 예: 내부 사정이 외부로 노출됨

```java
public record ReservationTimeRequestDto(
        LocalTime startAt
) {
    public ReservationTime toEntity(Long id) { // 받을 필요 없는 id
        return ReservationTime.builder()
                .id(id)
                .startAt(this.startAt)
                .build();
    }
}

// 호출부
ReservationTime saved = reservationTimeDao.save(requestDto.toEntity(null));
```

이 코드를 보면 다음과 같은 의문이 든다.

- "왜 `null`을 넣지? `null`이면 안 되는 거 아닌가?"
- "`null`을 넣으면 어떻게 되는 거지?"

**이유**: Service가 *"DB에서 ID는 저장 후에 자동 생성되기 때문에, 저장 전엔 ID가 없다"*는 DB 내부 사정을 알고 있어야 `null`을 넣을 수 있다. 즉, 영속성 계층의 구현 디테일이 상위 계층까지 새어나온 것.

### 개선: 외부에서 내부 사정을 몰라도 되도록

```java
public record ReservationTimeRequestDto(
        LocalTime startAt
) {
    public ReservationTime toEntity() {
        return ReservationTime.builder()
                .startAt(this.startAt)
                .build();
    }
}

// 호출부
ReservationTime saved = reservationTimeDao.save(requestDto.toEntity());
```
