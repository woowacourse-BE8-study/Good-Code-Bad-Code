## Chapter 10 문제: 테스트의 원칙

### 문제 1. 서비스 테스트가 통합 테스트로 동작한다
단위 테스트는 빠르고, 독립적이어야 한다. 느린 테스트는 실행을 기피하게 되고, 신뢰를 잃는다.

**현재 코드 (ReservationServiceTest.java:20-21)**
```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.NONE)
@DirtiesContext(classMode = DirtiesContext.ClassMode.BEFORE_EACH_TEST_METHOD)
class ReservationServiceTest {
  
      @Autowired
      private ReservationService reservationService;
 ```

* 문제점:
  * @SpringBootTest 는 Spring 컨텍스트 전체를 띄운다 → DB 연결, 빈 등록 등 모든 초기화 
  * @DirtiesContext(BEFORE_EACH_TEST_METHOD) 는 테스트 메서드마다 컨텍스트를 재생성 
  * 7개 테스트 메서드 × 컨텍스트 풀 재시작 = 수십 초 낭비 
  * 이건 서비스 단위 테스트가 아니라 DB까지 연결된 통합 테스트 
  * @DirtiesContext 가 필요한 이유가 뭔가? 
    * → 테스트들이 DB 시드 데이터를 공유 가변 상태로 쓰기 때문. 이게 근본 문제다.

**개선 방향 — 진짜 단위 테스트로:**

```java
// @SpringBootTest 제거, Mock/Fake 사용
class ReservationServiceTest {

    // 페이크(Fake): 실제 동작하는 경량 구현체
    private ReservationRepository reservationRepository = new FakeReservationRepository();
    private ReservationTimeService reservationTimeService = new FakeReservationTimeService();
    private ThemeService themeService = new FakeThemeService();
    private ReservationFactory reservationFactory = new ReservationFactory();

    private ReservationService reservationService = new ReservationService(
            reservationRepository, reservationTimeService, themeService, reservationFactory);

    @Test
    void 예약_생성_성공() {
        // 테스트 안에서 직접 상태 준비 → @DirtiesContext 불필요
        Theme theme = Theme.restore(1L, "테마1", "설명", "[https://image.com](https://image.com)");
        ((FakeReservationTimeService) reservationTimeService).register(time);
        ((FakeThemeService) themeService).register(theme);
        
        ReservationResponse response = reservationService.createReservation(
                new ReservationRequest("현미밥", LocalDate.now().plusDays(1), 1L, 1L));
                
        assertThat(response.id()).isNotNull();
        assertThat(response.name()).isEqualTo("현미밥"); // 약한 검증도 함께 보강
    }   
}
```   
▎ 책 10장: "페이크(Fake)는 실제처럼 동작하는 경량 구현체다. 목(Mock)보다 유연하고, 테스트가 구현 세부사항에 덜 묶인다."

### 문제 2. 테스트가 DB 시드 데이터의 마법 숫자 ID에 의존한다
테스트는 비결정적 요소(외부 상태, 특정 환경)에 의존해선 안 된다. 시드 데이터가 바뀌면 테스트 이유도 모르고 깨진다.

```java
void 예약_삭제_성공() {
    reservationService.deleteReservation(11L); // 왜 11? 시드 데이터의 몇 번째?
}   

void 과거_예약_취소_불가() {
    assertThatThrownBy(() -> reservationService.deleteReservation(1L)); // 왜 1이 과거?
}   

void 중복_예약_수정_불가() {
    reservationService.updateReservation(12L, ...); // 왜 12?
} 
```
* 문제점: 
  * 이 테스트들은 "id=11 은 미래 예약", "id=1 은 과거 예약", "id=12 는 특정 테마/날짜" 라는 시드 데이터 구조를 외워야만 이해 가능하다. 시드 데이터 한 줄만 바뀌어도 전부 무너진다.

**개선 방향 — 테스트 안에서 상태를 직접 만든다:**

```java
@Test
void 과거_예약은_취소할_수_없다() {
    // Arrange: 과거 예약을 직접 만들어서 저장
    Reservation pastReservation = Reservation.restore(
            null, "현미밥", LocalDate.now().minusDays(1), time, theme);
    Reservation saved = reservationRepository.save(pastReservation);
    
    // Act & Assert
    assertThatThrownBy(() -> reservationService.deleteReservation(saved.getId()))
            .isInstanceOf(PastTimeCancelException.class);
}
```
### 문제 3. 테스트 하나에 여러 개념이 섞여 있다
한 테스트는 하나의 시나리오만 검증해야 한다. 실패 시 무엇이 잘못됐는지 즉시 알 수 있어야 한다.

```java
@Test
@DisplayName("예약 삭제 후 해당 시간 예약 가능")
void 예약_삭제_성공() {
    // 삭제 전 상태 확인 (왜 여기서?)
    assertThat(reservationTimeService.getAvailableTimes(LocalDate.of(2099, 12, 1), 1L)).hasSize(1);
    
    reservationService.deleteReservation(11L); // 핵심 동작
    
    // ReservationService 테스트인데 ReservationTimeService를 검증 중
    assertThat(reservationTimeService.getAvailableTimes(LocalDate.of(2099, 12, 1), 1L)).hasSize(2);
}
```

* 문제점:
  * ReservationService 테스트인데 ReservationTimeService 결과를 검증
  * "삭제 성공" 과 "시간 해제 확인" 이 하나의 테스트에 묶임 
  * @DisplayName("예약 삭제 후 해당 시간 예약 가능") 인데 메서드명은 예약_삭제_성공 — 불일치

### 문제 4. 일관성 없는 검증 깊이
같은 계층의 테스트는 같은 수준으로 검증해야 한다. 어떤 건 ErrorCode까지, 어떤 건 예외 타입만 — 이런 불일치는 "무엇을 신뢰해야 하는가"를 모호하게 만든다.

```java
// 서비스 테스트 — ErrorCode + 메시지까지 검증 (ReservationServiceTest.java:43-45):
.satisfies(e -> assertThat(((BusinessException) e).getErrorCode()).isEqualTo(ErrorCode.TIME_NOT_FOUND))
.hasMessage(ErrorCode.TIME_NOT_FOUND.getMessage());

// 도메인 테스트 — 예외 타입만 검증 (ReservationTest.java:56-58):
assertThatThrownBy(() -> factory.create("현미밥", LocalDate.now().minusDays(1), time, theme))
    .isInstanceOf(BusinessException.class);
// ErrorCode 확인 없음
```

**개선 방향 — 도메인 테스트도 동일 수준으로:**

```java
@Test
void 과거_날짜면_예외_발생() {
    assertThatThrownBy(() -> factory.create("현미밥", LocalDate.now().minusDays(1), time, theme))
            .isInstanceOf(BusinessException.class)
            .satisfies(e -> assertThat(((BusinessException) e).getErrorCode())
                    .isEqualTo(ErrorCode.PAST_TIME_CREATE))
            .hasMessage(ErrorCode.PAST_TIME_CREATE.getMessage());
}
```

### 문제 5. 취약한 순서 기반 검증
구현 세부사항(내부 정렬 방식, 반환 순서)이 바뀌면 깨지는 테스트는 취약하다. 동작(behavior)을 검증해야지, 구현 방식을 검증하면 안 된다.

**현재 코드**
```java
void 인기_테마_조회() {
    List<ThemeResponse> result = themeService.getTopThemes(10);
    
    assertThat(result).hasSize(3);
    assertThat(result.get(0).name()).isEqualTo("테마A"); // 인덱스 직접 접근
    assertThat(result.get(1).name()).isEqualTo("테마B"); 
    assertThat(result.get(2).name()).isEqualTo("테마C");
}
```
* 문제점:
  * get(0), get(1), get(2) 로 인덱스 직접 접근 — DB 쿼리 정렬 변경 시 즉시 깨짐 
    * 순서가 중요하다면 containsExactly, 아니라면 containsExactlyInAnyOrder 로 의도를 명확히

**개선 방향:**
```java
void 인기_테마_조회_예약수_내림차순() {
    List<ThemeResponse> result = themeService.getTopThemes(10);
    
    // 순서가 중요한 경우: 의도를 테스트 이름과 검증 방식 모두에서 표현
    assertThat(result)
            .extracting(ThemeResponse::name)
            .containsExactly("테마A", "테마B", "테마C");
}           

@Test
void 인기_테마_조회_limit_적용() {
    List<ThemeResponse> result = themeService.getTopThemes(2);

    assertThat(result).hasSize(2);
}
```
### 문제 6. 예약 생성 성공 테스트의 약한 검증
테스트는 "이 코드가 돌아간다" 가 아니라 "이 코드가 올바르게 동작한다" 를 증명해야 한다.

**현재 코드 (ReservationServiceTest.java:32-35)**
```java
void 예약_생성_성공() {
    ReservationResponse response = reservationService.createReservation(
            new ReservationRequest("현미밥", LocalDate.now().plusDays(1), 1L, 1L));
            
    assertThat(response.id()).isNotNull(); // id만 확인
}
```

* 문제점: id != null 만 확인하면 이름이 틀려도, 날짜가 틀려도, 테마가 바뀌어도 테스트를 통과한다.

**개선 방향:**
```java
@Test
void 예약_생성_성공() {
    LocalDate tomorrow = LocalDate.now().plusDays(1);
    
    ReservationResponse response = reservationService.createReservation(
            new ReservationRequest("현미밥", tomorrow, 1L, 1L));
            
    assertThat(response.id()).isNotNull();
    assertThat(response.name()).isEqualTo("현미밥");
    assertThat(response.date()).isEqualTo(tomorrow);
    assertThat(response.themeId()).isEqualTo(1L);
}
```
