## 1장. 코드 품질

### 코드 작성시 4가지 상위 수준의 목표
* 작동해야 한다.
* 작동이 멈춰서는 안 된다.
* 변화하는 요구 사항에 적응해야 한다.
* 이미 존재하는 기능을 또다시 구현해서는 안 된다.

### 코드 품질의 여섯 가지 핵심 요소
* 코드는 읽기 쉬워야 한다.
> 💡 코드가 하는 일, 어떻게 그 일을 수행하는지, 어떤 것을 필요로 하는지, 코드 실행 결과물을 바로 이해할 수 있게 코드의 가독성 중요!

* 코드는 예측 가능해야 한다.
* 코드를 오용하기 어렵게 만들라.
* 코드를 모듈화하라.
> 💡 모듈화 : 개체나 시스템의 구성 요소가 독립적으로 교환되거나 교체될 수 있음을 의미
> 
> → 모듈화된 시스템의 주요 특징 : 인터페이스가 잘 정의되어 서로 다른 구성 요소 간 상호작용하는 지점이 최소화
> 
> 코드를 외부에 의존하지 않고 실행할 수 있는 모듈로 나누자
> 
> 이때 두 개의 인접한 모듈 사이의 상호작용은 한 곳에서 일어나고 잘 정의된 인터페이스를 사용

* 코드를 재사용 가능하고 일반화할 수 있게 작성하라.
> 💡 재사용성 : 어떤 문제를 해결하기 위한 무언가가 여러가지 다른 상황에서도 사용 가능
> 
> ex) 핸드드릴 : 벽, 바닥 및 구멍을 뚫는데 사용할 수 있어 재사용 가능
> 
> → 문제는 동일하지만 (구멍 뚫기) 상황은 다르다 (벽을 뚫는거랑 바닥을 뚫는건 다름!)
> 
> 일반화성 : 개념적으로 유사하지만 서로 미묘하게 다른 문제들을 해결
> 
> 구멍 뚫는 것 뿐만 아니라 나사를 박을 때도 사용!
> 
> → 무언가를 돌린다는 것은 드릴로 구멍을 뚫는 일과 나사를 돌려 넣는 일에 둘 다 적용할 수 있는 일반적인 문제

* 테스트가 용이한 코드를 작성하고, 제대로 테스트하라.
> 💡 단위테스트 : 개별 함수나 클래스와 같은 작은 단위의 코드를 테스트
> 
> 통합 테스트 : 시스템은 일반적으로 여러 구성 요소, 모듈, 하위 시스템으로 구성, 이러한 구성 요소와 하위 시스템을 함께 연결하는 과정 → 통합
> 
> → 통합테스트를 통해 이러한 구성 요소들이 제대로 작동하고 멈추지 않고 계속 실행하는지 확인
> 
> 종단간 테스트 : 처음부터 끝까지 전체 소프트웨어 시스템에서 작동의 흐름을 테스트 (E2E 테스트)

### 1장 요약
* 좋은 소프트웨어를 만들려면 고품질 코드를 작성해야 한다.
* 실제 서비스 환경에서 실행되는 소프트웨어가 되기 전에 코드는 일반적으로 여러 단계의 검사와 테스트를 통과해야 한다(때로는 수동, 때로는 자동화를 통해)
* 버그나 제대로 동작하지 않는 기능이 사용자에게 제공되거나 비즈니스에 중요한 시스템에서 실행 되는 것을 이러한 검사를 통해 막을 수 있다.
* 테스트는 코드를 작성하는 모든 단계에서 고려하는 것이 좋다. 코드를 다 작성하고 난 후에 고려 하는 것이 아니다.
* 고품질 코드를 작성하면 처음에는 시간이 오래 걸리지만, 중장기적으로는 개발 시간이 단축되는 경우가 많다.

## 2장. 추상화 계층

* 함수를 작게 만들고 수행하는 작업 → 코드의 가독성과 재사용성 up

### 클래스
* 응집력 : 한 클래스 내의 모든 요소들이 얼마나 잘 속해있는지를 보여주는 척도
* 좋은 클래스는 응집력이 매우 강하다
* 순차적 응집력 : 한 요소의 출력이 다른 요소의 입력으로 필요할 때 발생
    * 원두를 갈기 전에는 커피를 추출할 수 없다
    * 원두를 갈아내는 과정의 산출물은 커피를 추출하는 과정에 투입
* 기능적 응집력 : 몇 가지 요소들이 모여서 하나의 일을 성취하는 데 기여할 때 발생
* 관심사의 분리 : 시스템이 각각 별개의 문제를 다루는 개별 요소로 분리되어야 함
    * 게임 콘솔은 티비와 동일한 제품으로 묶이지 않고 티비와 분리
* 클래스는 응집력이 있어야 하고 한 가지 일에만 관심을 가져야 한다.

* 여러 함수로 나누어 추상화 계층을 만들었지만, 여전히 하나의 클래스가 모든 걸 가지고 있고 클래스를 풀 때 하위 문제를 다 풀어야 한다면 → 추상화 계층들 사이의 분리가 그다지 뚜렷하지 않다.
    * 클래스가 여러 하위 문제를 해결하는 코드를 가지고 있음

### 저품질 코드임을 확인하기 위한 여러 근거
* 코드를 읽을 수 없다
* 코드가 특별히 모듈화되어 있지 않다.
* 코드를 재사용할 수 없다.
* 코드를 일반화할 수 없다.
* 코드를 제대로 테스트 하기 어렵다.
  * → 의존성 주입으로 해결
  * → 클래스 구조를 설계할 때 코드 품질의 근거를 충족하는지 생각하면 좋다.

### 인터페이스
* 추상화 계층을 깔끔하게 구현하는 코드를 만드는데 있어 매우 유용함
  * 주어진 하위 문제에 대해 둘 이상의 서로 다른 구체적인 구현이 가능
  * 구현 클래스 사이에 전환이 필요할 때는 추상화 계층을 나타내는 인터페이스를 정의하는 것이 가장 좋다
  * → 모듈화, 재설정 👍

* 코드를 별개의 계층으로 세분화하면 추가 비용이 발생
  * 클래스를 정의하거나 의존성을 새 파일로 임포트하려고 반복적으로 사용하는 코드로 인해 코드의 양이 늘어난다.
  * 로직의 이해를 위해 파일이나 래스를 따라갈 때 더 많은 노력이 필요
  * 인터페이스 뒤에 계층을 숨기게 되면 어떤 상황에서 어떤 구현이 사용되는지 파악하는 데 더 많은 노력이 필요
  * 로직 이해나 디버깅 하는 것이 어려워짐
  * 그래도 너무 많은 계층을 남용하는 결과를 가져오더라도 계층을 여러개로 나누는 것이 한 계층 안에 모든 코드를 집어넣는 것보다 낫다.

public interface CannonRule {

### 마이크로서비스
* **마이크로서비스 아키텍쳐**: 
  * 개별 문제에 대한 해결책이 단지 단일 프로그램으로 컴파일되는 라이브러리 수준이 아니라 독립적으로 실행되는 서비스로 배포
    * 시스템이 여러가지 소규모 프로그램으로 분할되어 특정 작업만 전문적으로 수행
  * 시스템을 분리하여 보다 모듈화할 수 있는 매우 좋은 방법이지만, 서비스를 구현하기 위해 여러 하위 문제를 해결해야 한다는 사실은 바뀌지 않음!

### 2장 요약
* 코드를 깨끗하고 뚜렷한 추상화 계층으로 세분화하면 가독성, 모듈화, 재사용, 일반화 및 테스트 용이성이 향상
* 특정 언어에 국한된 기능뿐만 아니라 함수, 클래스 및 인터페이스를 사용하여 코드를 추상화 계층으로 나눌 수 있다
* 코드를 추상화 계층으로 분류하는 방법을 결정하려면 해결 중인 문제에 대한 판단과 지식을 사용
* 너무 비대한 계층 때문에 발생하는 문제는 너무 얇은 계층 때문에 발생하는 문제보다 더 심각하다. 확실하지 않은 경우에는 남용의 위험에도 불구하고 계층을 얇게 만드는 것이 좋다

## 3장. 다른 개발자와 코드 계약

* 다른 개발자가 변경하거나 코드와 상호작용할 때 발생할 수 있는 문제는 없는지, 또 발생한다면 그 문제를 어떻게 완화할 수 있을지를 이해하고 선제적으로 조치
* **다음 3가지를 고려하자**
  * 자신에게 명백하다고 해서 다른 사람에게도 명백한 것은 아니다.
  * 다른 개발자는 무의식중에 여러분의 코드를 망가뜨릴 수 있다.
  * 시간이 지남에 따라 자신의 코드를 기억하지 못한다.

* **다른 개발자의 코드를 읽을 때 어떻게 사용해야하는지 알아내기 위해 할 수 있는 일**
  * 함수, 클래스, 열거형 등의 이름을 살펴본다.
  * 함수와 생성자의 매개변수 유형 또는 반환값의 유형 같은 데이터 유형을 살펴본다.
  * 함수/클래스 수준의 문서나 주석문을 읽어본다.
  * 직접 와서 묻거나 채팅/이메일을 통해 문의한다.
  * 여러분이 작성한 함수와 클래스의 자세한 구현 코드를 읽는다.

### 세부 조항을 제거하는 방법
* 세부 조항에 의존하기 보다는 잘못된 일을 하는 것을 처음부터 불가능하게 만들자
* 어떤 항목에 대해 발생 자체가 불가능 하도록 명백한 항목으로 바꾸자
* ⇒ 상태나 가변성이 클래스 외부로 노출되는 것을 없애자

> 👾 **실제 코드**
>
> **변경 전: 상태 통제권이 외부에 노출된 구조**
>   
> - Jackson 역직렬화를 위해 `public ReservationTime()`을 열어두면, 애플리케이션 내 어떤 코드에서든 `new ReservationTime()`을 호출해 내부 필드가 모두 null인 빈 객체를 생성할 수 있음  
> 
> - 기본 생성자가 열려 있으면 도메인 규칙을 무시한 불완전한 상태의 객체가 외부에 의해 언제든 만들어질 수 있음. 객체의 상태 제어권이 클래스 외부로 완전히 노출된 것
> 
> **변경 내용: DTO 도입을 통한 책임 분리와 생성자 은닉**
> 
> - `ReservationTimeRequest` DTO를 만들어 Jackson이 요구하는 역직렬화 책임을 DTO로 완전히 넘겼습니다.
> 
> - DTO가 외부 입력을 대신 받아줌으로써, `ReservationTime` 도메인 객체의 public 기본 생성자를 제거. 도메인 객체는 유효한 값을 모두 인자로 받는 생성자만을 외부에 제공
> 
> - 이제 외부에서는 값이 채워지지 않은 `ReservationTime` 객체를 절대 생성할 수 없음

> 💡 **코드 품질을 향상시키기 위해서는 상태나 가변성을 최소화하자**
> * **상태** : 객체가 담고있는 어떤 값이나 데이터
> * 객체를 만든 후 이러한 객체의 상태를 수정할 수 있으면 이 객체는 가변적
>
> 🤓 **상태나 가변성을 최소화 하는 방법**
> 1. **불변객체 활용**
>    * → 상태 변경 대신 새로운 객체 반환 : 값을 수정해야 할 때 기존 객체를 바꾸지 말고, 수정된 값을 가진 새로운 객체를 생성하여 반환
>    * → 자바 : `final` 사용 , 코틀린 : `val` 사용
> 2. **캡슐화**
>    * → 객체 내부의 상태를 외부에서 직접 수정하지 못하도록 메서드(Setter) 제공을 지양
> 3. **방어적 복사**
>    * 객체 내부의 가변 요소(예: 리스트, 배열)를 외부로 전달하거나 외부에서 받을 때, 원본의 참조를 그대로 전달하지 않고 복사본을 만들어 전달하는 방법
>    * → Java의 `Collections.unmodifiableList()`를 사용
> 4. **기본 자료형 대신 값 객체(Value Object, VO) 사용**
>    * 숫자나 문자열 같은 기본 타입을 직접 노출하지 않고, 이를 감싸는 작은 불변 객체를 만듭니다.
>    * 방법: `int money` 대신 `Money` 클래스를 만들어 그 안에 불변 로직을 넣습니다.
>    * 이유: `money = money - 100` 같은 가변 연산 대신 `money.minus(100)`을 통해 새로운 `Money` 객체를 반환하게 유도함으로써 데이터의 무결성을 지킵니다.

### 오류를 확인할 수 있는 방법
* 체크 및 어서션
* 런타임 검사
* 컨파일 타임만큼 강력 X

> 💡 🤓 **컴파일 타임 vs 런타임**
> * **컴파일 타임** : 개발자가 작성한 소스 코드를 컴퓨터가 이해할 수 있는 기계어(또는 바이트코드)로 변환하는 시점
>   * → 주체 : 컴파일러
>   * → 특징: 소스 코드의 구문 오류(Syntax Error)나 타입 체크를 수행
> * **런타임** : 컴파일을 마친 프로그램이 실제로 메모리에 올라가 실행되는 시점 (문법은 완벽하지만, 실행 중에 환경이나 데이터 때문에 터짐)
>   * → 주체: 사용자 및 컴퓨터 CPU/메모리
>   * → 특징: 프로그램 실행 중에 발생하는 논리적 오류나 환경적인 요인에 의한 문제가 드러남
>
> **Q. 왜 런타임은 컴파일 타임만큼 "강력"하지 않을까?**
> * **사전 차단 vs 사후 약방문**: 컴파일 타임 오류는 개발자 PC에서 이미 발견됩니다. 즉, 사용자에게 나쁜 경험을 줄 기회조차 없습니다. 반면 런타임 오류는 사용자의 폰이나 PC에서 발생하므로 서비스 신뢰도에 치명적입니다.
> * **전수 조사 vs 부분 실행**: 컴파일러는 소스 코드 전체를 훑으며 모든 경로를 검사합니다. 하지만 런타임 오류는 특정 조건(예: 사용자가 이상한 값을 입력함)이 맞아야만 터지기 때문에, 테스트 단계에서 발견하기가 훨씬 어렵습니다.
> * **성능과 비용**: 컴파일 타임에 타입을 체크하면 실행 중에는 "이게 숫자인가?"라고 확인할 필요가 없어 프로그램 속도가 빠릅니다. 런타임에 모든 것을 확인하려 하면 프로그램이 무거워지고 느려집니다.
>
> | 구분 | 컴파일 타임 | 런타임 |
> | --- | --- | --- |
> | **시점** | 실행 파일 생성 시 | 프로그램 실행 중 |
> | **오류 발견** | 컴파일러가 문법/타입 체크 | 사용자가 실행 중 예외 발생 |
> | **안정성** | 높음 (미리 걸러냄) | 낮음 (예측 불가능) |
> | **예시** | 세미콜론 누락, 타입 불일치 | 0으로 나누기, Null 참조, 메모리 부족 |

### 체크
* 코드 계약이 준수되었는지 확인하기 위한 추가 로직
* 입력 매개변수에 대한 제약 조건 또는 수행해야 할 설정에 대한 제약
* 준수되지 않으면 체크는 실패하는 오류를 생성
* 이 실패는 명백해서 놓치고 넘어가는 것이 불가능
* 전제 조건 검사 : 입력 인수가 올바르거나 초기화가 수행되었거나, 일부 코드를 실행하기 전에 시스템이 유효한 상태인지 확인하는 경우
* 사후 상태 검사 : 반환값이 올바르거나 일부 코드를 실행한 후 시스템이 유효한 상태인지 확인하는 경우
* 퍼즈 테스트 : 잘못된 설정을 드러낼 수 있는 입력값을 생성해 테스트를 수행

### 어서션
* 컴파일에서 제외
* 코드가 실제 서비스 환경에서 사용될 떄 실패를 명백하게 보여주지 않음

### 3장 요약
* 코드베이스는 계속 변하고 일반적으로 여러 개발자에 의해 변경된다.
* 다른 개발자가 어떻게 코드를 해석하고 오용할 수 있을지 생각해보고, 이러한 가능성을 최소화하거나 오용이 불가능하게 만드는 방식으로 코드를 작성하는 것이 유용하다.
* 코드를 작성할 때 일종의 코드 계약이 항상 만들어진다. 여기에는 명백한 항목이나 세부 조항과 같은 내용이 포함될 수 있다.
* 코드 계약의 세부 조항은 다른 개발자가 계약을 준수하도록 하기 위한 방법이지만 신뢰할만한 방법은 아니다. 보통 더 나은 접근법은 명백한 항목으로 계약의 내용을 전달하는 것이다.
* 일반적으로 컴파일러를 사용하여 계약을 확인하는 것이 가장 신뢰할 수 있는 방법이다. 이것이 가능하지 않을 때, 체크나 어서션을 사용하여 실행 시간에 계약을 확인할 수 있다.
